# 🛤️ HTTP Pipeline & Middleware

## 1. Philosophy / Purpose
In Ferrox PHP, the HTTP Pipeline is the indestructible outer shell of the application. Its purpose is to guarantee that no unhandled exception, syntax error, or database failure ever leaks raw stack traces to the client. It standardizes the request lifecycle into a predictable, sterile, and observable flow.

## 2. Architectural Layering
The Pipeline exists at **Layer 1 (Entrypoint) and Layer 2 (Guards)** of the Onion Architecture. It wraps the entire application. When the underlying execution engine (Swoole/RoadRunner) receives a raw TCP request, it is immediately fed into this Pipeline.

## 3. Core Concepts (For Neophytes)
Think of the Pipeline as a water filter. The HTTP Request is the dirty water. It passes through multiple filters (`MiddlewareInterface`) before it is clean enough to reach your Application Logic.
If any filter detects a problem (e.g., missing auth token), it immediately returns an HTTP Response (e.g., 401 Unauthorized), and the water never reaches the application.

```php
use Ferrox\Core\Http\Pipeline;

$pipeline = new Pipeline($container, [
    MandatoryComplianceMiddleware::class,
    SentinelThreatEngineMiddleware::class,
    PasetoAuthGuard::class
], $routerHandler);

$response = $pipeline->handle($request);
```

## 4. How it Works Under the Hood
The Pipeline implements the **Chain of Responsibility** design pattern combined with a global `try/catch` safety net. 

When `$pipeline->handle()` is called, it recursively invokes the `process()` method of each middleware. 
Crucially, the entire execution is wrapped to comply with **OWASP WSTG-INPV-005**. If an internal component (like a Database Repository) panics and throws an unhandled `PDOException`, the Pipeline catches it, logs the raw stack trace via OpenTelemetry/Monolog, and sanitizes the output into a generic `500 Internal Server Error` JSON response.

## 5. Why it was designed this way
Traditional PHP frameworks (like Laravel) rely on a global Exception Handler that is often tightly coupled to the HTTP Kernel. In memory-resident environments like RoadRunner, a leaked exception can kill the entire worker thread, dropping hundreds of concurrent connections. The Ferrox Pipeline is designed to trap the exception *inside* the request scope, keeping the worker alive and healthy.

## 6. Anti-Patterns
- **❌ Bypassing the Chain**: Calling `$handler->handle($request)` without returning its output.
- **❌ Echoing Output**: Using `echo`, `print`, or `die()` inside a middleware. This corrupts the HTTP buffer and destroys the JSON-RPC standard.
- **❌ Statefulness**: Storing request-specific data in class properties of a Middleware. Middlewares are singletons in RoadRunner; their properties will leak across concurrent requests.

## 7. Enterprise Usage (For Seniors)
In an Enterprise context (e.g., highly concurrent ERP webhook ingestion), the Pipeline is where distributed tracing (Jaeger/Zipkin) begins.
You can inject a `TracingMiddleware` as the very first link in the chain. It reads the `X-B3-TraceId` header from the load balancer, attaches it to a Context object, and passes it down. This ensures that every SQL query, Redis lookup, and Outbox event generated by this request shares the exact same Trace ID.
